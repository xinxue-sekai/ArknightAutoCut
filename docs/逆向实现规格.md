# NewCut · 逆向实现规格说明书

> 本文回答两个问题：**原工具到底做了什么**（通过对其行为与素材的分析得出），以及 **NewCut 如何用完全自研的代码实现同样的功能**。NewCut 不包含原项目的任何代码或资源文件；原项目仅作为功能规格的参考。
>
> 分析对象：liemark/arknight-auto-editing（本地副本）；产线代码：`service/newcut_service/nc_*.py`。

---

## 1. 功能规格的逆向过程

### 1.1 状态判定依据是什么？—— UI 取证

对原项目附带的四张基准截图（1920×1080）做模板定位与差分分析，得到明日方舟战斗界面右上角控制条的确切布局：

```
…                        ┌─────────┬─────────┐
                         │  1X ▶   │   ❚❚    │   ← 运行中(1倍速)
                         ├─────────┼─────────┤
                         │  2X ▶▶  │   ❚❚    │   ← 运行中(2倍速)
                         ├─────────┼─────────┤
                         │ ▶▶▶(置灰)│    ▶    │   ← 已暂停
                         └─────────┴─────────┘
                          速度键(左)   播放/暂停键(右)
                          x≈0.82-0.90  x≈0.91-1.00（归一化）
```

定位方法：把原项目的模板小图在全屏截图中做 NCC 滑窗匹配（得分 ≈1.0 处即裁剪原点），得到：

| 原模板 | 位置（1920×1080） | 归一化 |
|--------|------------------|--------|
| pause 三张（中央菜单部件） | (913~1161, 480~602) | x≈0.48-0.60, y≈0.44-0.55 |
| 1x | (1609, 40) | (0.838, 0.037) |
| 2x | (1605, 39) | (0.836, 0.036) |
| play（▶ 键） | (1768, 54) | (0.921, 0.050) |

### 1.2 原工具的状态模型（及其缺陷）

| 原工具 | 检测物 | 问题 |
|--------|--------|------|
| PAUSE | **屏幕中央的暂停菜单**（三张裁剪） | 依赖菜单 overlay，转场动画期间可能漏检 |
| 1x / 2x | 右上速度键文字 | ✓ 合理 |
| 0.2x（"play"） | 右上**暂停键显示 ▶** | 语义错误：▶ 是"已暂停"标志，不是 0.2 倍速；且其 0.2x 源截图与 2x 源截图是同一个文件（md5 相同），0.2x 检测实际从未有独立依据 |

### 1.3 NewCut 的状态模型（更正后）

**直接读两个按钮的图标，检测即语义**：

| 状态 | 判据（右上控制条） | 常量 |
|------|--------------------|------|
| PAUSED | 右键 = ▶ | `STATE_PAUSED` |
| SPEED_1X | 右键 = ❚❚ 且 左键 = 1X▶ | `STATE_SPEED_1X` |
| SPEED_2X | 右键 = ❚❚ 且 左键 = 2X▶▶ | `STATE_SPEED_2X` |
| NORMAL | 右键 = ❚❚ 但左键不可识别 / UI 不在屏 | `STATE_NORMAL` |

原工具的"0.2x 加速 10 倍"功能在新模型下并入 PAUSED 的处理（▶ 状态的真实含义），不再单列。`▶▶▶` 置灰图标是暂停时速度键的禁用态，不构成独立状态。

## 2. 算法规格（行为等价，实现原创）

### 2.1 逐帧分类（nc_match.py，v2）

- 帧**等比缩放**到模板包处理分辨率（默认 640×400，宽高不符时黑边填充，杜绝拉伸变形）→ 灰度
- **掩码 NCC**：模板按亮度阈值（默认 >130）二值化，只匹配亮色图标像素（抗底板/背景干扰；该设计取自原项目 load_templates 的掩码思想）
- **限定区域全帧搜索**：在画面右上搜索窗（默认 x≥0.35, y≤0.55）内滑窗匹配，**不假设 UI 固定位置**——吸收窗口化录制、标题栏偏移、不同分辨率的布局差异（v1 的"ROI 裁片=补丁零容差"设计在 16:10/带标题栏素材上全部落空，教训记录于此）
- 判定顺序：playpause 组最佳匹配 paused(▶) 且过阈值 ⇒ PAUSED；= running(❚❚) ⇒ 看 speed 组（1X/2X 过阈值）；否则 NORMAL
- 阈值默认 0.75。校准自检（用户 1200p 素材）：暂停帧→PAUSED、运行帧→SPEED_2X 均正确；v1 夹具交叉验证矩阵：自匹配 1.000，异状态最高 0.620

### 2.2 分段与暂停处理（nc_segment.py）—— 原工具的核心价值

1. **游程分段**：连续同状态帧为一段
2. **暂停段运动分析**：段内帧差 `diff[i] = mean|gray[i]−gray[i−1]|`；`diff > motion_thresh`(默认 2.0) 视为有效操作（连带点亮前一帧起手帧）；静止游程长于 `still_frames`(默认 0.1s) 则删除——段首静止保留尾部缓冲、段尾静止保留头部缓冲、中部静止两端对半缓冲；整段无操作时删中段留两端缓冲
3. **边界差分规则**（保留原工具语义）：暂停段前一帧 vs 后一帧的差分 < `boundary_thresh`(默认 5.0) ⇒ 暂停前后画面几乎一致（暂停只是在跳转场/加载）⇒ **无论段内是否有操作，整段全删**
4. **倍速段**：1x 段标记为"建议 2 倍速"。PR 重建模式不抽帧（与原工具导出抽帧的差异见方案文档 §4），由 PR 原生速度实现等价效果

### 2.3 与原工具实现的差异清单

| 项 | 原工具 | NewCut | 理由 |
|----|--------|--------|------|
| 暂停检测 | 中央暂停菜单模板 | 右上 ▶ 键 | 语义直接，转场更稳 |
| 0.2x 状态 | ▶ 键误判为 0.2x + 10 倍抽帧 | 并入 PAUSED | UI 取证更正 |
| 边界差分二次扫描 | 分析上下文缓存优化 | 顺序 grab 单次扫描（简单直接） | 暂停段数量少，整段扫描代价秒级，不值得引入缓存失效逻辑 |
| 解码并行 | 多进程 ProcessPool + IPC 灰度图 | 单进程读帧 + 线程池分类（matchTemplate 释放 GIL） | 少一层序列化复杂度；瓶颈在读帧（实测占比 ~50%），并行收益有限 |
| 导出 | FFmpeg trim/concat + GPU 探测 | 无（PR 原生重建） | 插件直接编辑序列，不产出中间视频 |
| 依赖 | numpy/opencv/pillow/imageio/imageio-ffmpeg | numpy + opencv | 只分析不导出 |

## 3. 模板包（自研资产格式）

```
newcut_service/template_pack/          ← 默认位置（不随仓库分发）
├─ manifest.json   { version, proc_size:[480,270], rois:{speed,playpause}, patches:[{name,state,roi,thresh,file}] }
├─ paused.png      右键 ▶ 补丁
├─ running.png     右键 ❚❚ 补丁
├─ speed1x.png     左键 1X▶ 补丁
└─ speed2x.png     左键 2X▶▶ 补丁（可选）
```

生成方式（一次性，用自己的基准截图）：

```bash
cd service
uv run python tools/calibrate.py --paused 暂停截图.png --run1x 运行1x截图.png --run2x 运行2x截图.png --verify
```

`--verify` 输出交叉分数矩阵用于人工确认可分性。截图分辨率不限（16:9），校准时统一缩放到处理分辨率再裁补丁；分析服务运行时必须使用同一处理分辨率（manifest 内记录并强制）。

`tests/fixtures/` 下的三张截图**只是测试夹具**（冒烟测试用它们合成视频、验证引擎端到端），不参与服务运行。

## 4. 服务契约（面板 ↔ 服务，v2 起）

| 端点 | 说明 |
|------|------|
| GET /status | `{ok, service, version, python}` |
| POST /probe | `{video_path}` → `{fps, frame_count, width, height, duration_sec}` |
| POST /analyze | `{video_path, params}` → `{job_id}`；params 可覆盖 `template_dir / thresholds(paused,running,speed1x,speed2x) / still_time_thresh / motion_thresh / boundary_thresh / speedup_1x / proc_* / batch / n_threads` |
| GET /job/{id} | `{state, phase, pct, detail, result?, error?}`；result 为剪辑方案 JSON（pauses/speeds/keep_ranges/delete_ranges/时长统计） |

面板侧（panel/）与本契约解耦，引擎替换对面板透明。

## 5. v0.3 增补：解码自适应与审阅功能

- **解码自适应（decode.py）**：不预设显卡品牌。分析启动时对候选硬件后端
  （cuda/qsv/d3d11va/dxva2/videotoolbox/vaapi/软解）各试解 96 帧实测，
  最快者胜出（硬解需快 10%+ 才优先，失败自动回退），全会话缓存选型。
  候选来自 `ffmpeg -hwaccels` 与实际解码测试的交集。强制指定后端时若
  探测未达标，显式告警回退（`backend_warning` 字段），不静默降级。
- **暂停段列表 / 缩略图 / 播放头跳转**：方案含每段 id 与时间，面板懒加载
  `/thumb` 缩略图，点击经 `/thumb` 之外的 `ncSeekPlayhead` 跳转 PR。
- **碎片合并**：相邻删除段间 <merge_gap_sec 的保留缝隙并入删除
  （消除暂停菜单淡入淡出造成的碎片段）。
- **转场删除**：黑屏（均值 <22 且 >0.4s）与冻结（NORMAL 态且帧差 <0.6
  持续 >1.2s，快速模式下禁用）两类段自动删除。
- **快速模式**：每 fps/12 帧采样 + 前值填充，分类耗时降为 1/N；代价是
  短暂停可能整段漏检（实测 582 → 147 段），默认关闭。
